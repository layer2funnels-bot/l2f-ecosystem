## V4-27 Client access, Door A (invite first) (PR 15)
- **One registry, `client_access` (migration 0032).** One row per client contact per organization: which client record, e-mail, status (`requested`, `invited`, `active`, `suspended`, `rejected`, `revoked`), source (`invite` now, `request` later), the signed-in identity once they accept, who decided and when. Membership stays the real switch: an active client has a `memberships` row (kind client, bound to ONE client record); suspend sets it `deactivated`, revoke deletes it; the registry follows through triggers, so even the older routes (`invitation.create` with kind client, `members.remove`) keep it honest.
- **The invite is one all-or-nothing step** (`client_access_invite`): finds or creates the client record (Onboarding stage, lead), cancels any older link for that e-mail, issues the invitation, records the access and history. No duplicates: same e-mail asks again = same access and client, new link; a record already carrying that e-mail is linked, not copied; two records with that e-mail = a plain "choose one"; a team member's e-mail is refused; a person who already has access is refused. If anything fails, nothing is kept except one `failed` event with a code, the caller is told `ok = false`, and retrying is safe.
- **Nothing is granted by signing up.** Accepting needs the invitation token AND a sign-in e-mail equal to the invited one (existing rule). A client can never choose a workspace, role or status. Only people with the new sensitive permission `clients.access.manage` (admin and owner by default) can invite, list, suspend, restore or revoke, always for the organization of the request; row security, a status-transition guard and an append-only history sit under it. Direct writes to the registry are impossible even for an owner.
- **Gate G2 is unchanged.** The Portal opens per organization only by the owner's switch (`workspace_apps` row for `portal`, off by default). An active client with the Portal off sees no app and every Portal call answers not found; the Admin tab says so in words and nothing in it can open the Portal.
- **Admin › Client access** lists each person (client, status, since), invites (email, name, existing or new client record), shows the one-time invitation link (e-mail sending is a go-live step), and offers send-a-new-link, cancel, suspend, restore, revoke, invite again, plus a plain-words history without e-mail addresses.
- **Door B fits without redesign**: `requested` / `rejected` and source `request` are already allowed; a request would create a `requested` row (no invitation, no membership) and approving it is the same move into `invited` and then `active`. Not built: it needs a public path and a spam decision.
- Sense-check: (1) The invitation e-mail is not sent automatically yet (SMTP at go-live); staff pass the link on. (2) Sign-in e-mail trust depends on "confirm e-mail" being ON in the live Supabase project (dashboard setting; in the runbook). (3) Suspending does not end a signed-in client's token, but every request is refused at once because access is checked per request. (4) A friend tester who is not an employee needs the same written Supabase answer as clients (docs/SUPABASE_TERMS_REQUEST.md); until then testers use only synthetic data. (5) `sensitive` calls are limited to 5 a minute per person, which is enough for one admin.

## V4-28 Weather: MET Norway terms applied (PR 15)
- User-Agent default is now `Layer2FunnelsAurjOffice/1.0 layer2funnels@gmail.com` (the owner's contact); `WEATHER_USER_AGENT` overrides it. Calls stay server-side.
- Caching follows MET's `Expires`: no new request before it (kept between 1 minute and 2 hours; 30 minutes if MET sends none), `If-Modified-Since` on refresh, a 304's Expires extends freshness, a stale answer is served up to 3 hours if MET is down. Coordinates still rounded to 2 decimals.
- Attribution shown: "Data from MET Norway" linked to met.no, the licence link (CC BY 4.0, https://creativecommons.org/licenses/by/4.0/) and "Changed: reduced to a one-line summary." MET's licence page says NLOD 2.0 and CC BY 4.0; the CC BY deed allows commercial use. The NLOD page could not be read (HTTP 406), so rely on CC BY.
- **Cloudflare Free cost (measured in Node/V8, `node scripts/weather-cost.mjs`)**: one weather request that misses the cache is about 1 ms of CPU (p99 about 2.4 ms) for the parse and about 0.3 ms (p99 0.7) for the sign-in check, 1 outside call (a cache hit is 0); the free limits are 10 ms CPU and 50 outside calls per request. **The database connection is the problem**: opening a connection with the password handshake costs about 5 ms of CPU per request and the transaction about 1 ms more (mean 6.8, p99 14.5 on the local stack), so any API request can exceed the 10 ms free limit. This was measured without TLS in Node, not in Cloudflare's runtime, so it must be confirmed with a live test (the go-live gate). Free ways to reduce it: Hyperdrive (free: 100,000 queries a day, so about 20,000 requests a day at five queries each, unverified how it changes the Worker's own handshake cost) and fewer statements per request. The certain fix is Workers Paid at $5 a month (30 ms default, up to 5 minutes), which needs the owner's approval.

## V4-29 Fewer database messages per request (PR 16)
- The per-request setup (begin, switch to the API role, claims, headers) now goes to the database as ONE message when the connection supports it (the real server does; values escaped by the driver), so a request is three messages instead of five. This cuts latency for a database far from the Worker (Pakistan to Mumbai) and the query count if Hyperdrive's free 100,000 a day is used. It does not remove the connection's password handshake, which is the larger CPU cost (V4-28); that still needs the live CPU test. Verified on the real local Supabase stack (71/71 checks) and with unit checks (`test/pg-executor.test.mjs`).
